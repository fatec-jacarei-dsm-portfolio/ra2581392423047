### README.md

## Contexto

Proyecto académico para practicar cálculo geográfico e integración entre frontend y backend: simular una ruta de vuelo real entre dos puntos aleatorios de Brasil, teniendo en cuenta la curvatura de la Tierra en lugar de una línea recta en un plano cartesiano.

## Mi rol

Desarrollé yo solo tanto el frontend como el backend.

## Solución

El frontend renderiza el mapa con Leaflet, permite ingresar coordenadas manualmente o hacer clic directamente en el mapa, y simula la trayectoria de la aeronave en tiempo real. El backend entrega coordenadas válidas dentro del territorio brasileño y, en cada actualización de posición, devuelve información geográfica (país, estado, municipio, microrregión y mesorregión) a partir de la API del IBGE.

## Decisiones técnicas

El cálculo de la posición a lo largo de la ruta usa interpolación esférica (Slerp) sobre el arco de círculo máximo entre las dos coordenadas, en lugar de interpolación lineal. Esto garantiza que la trayectoria represente la curvatura real de la Tierra y no una línea recta en un plano cartesiano. El backend fue reescrito en diciembre de 2025, estructurado en capas de rutas, controllers y services, con pruebas unitarias usando Jest.

## Resultado

El frontend está en línea y funciona de forma aislada, pero apunta a una versión anterior del backend (rutas antiguas), ya que el backend fue reescrito después del último ajuste del frontend. Por eso el panel de localidad durante el vuelo siempre devuelve "Desconhecido" (Desconocido), un bug documentado en la [issue #3](https://github.com/felipe-sant/maps-front/issues/3).

## Aprendizajes

Entender la diferencia entre interpolación lineal y esférica para cálculos geográficos, y la importancia de mantener sincronizados el frontend y el backend cuando son repositorios separados. La ruptura de compatibilidad solo se notó en una revisión posterior de los proyectos.

### README.md

## Contexto

Proyecto personal para practicar el ciclo completo de un producto con IA: entrenar un modelo de reconocimiento de dígitos manuscritos y exponerlo en una aplicación web interactiva, desde el dibujo hasta la predicción.

## Mi rol

Desarrollé yo solo las tres capas: el frontend (canvas de dibujo), el backend (intermediario entre front e IA) y el servicio de inferencia en Python, además de entrenar el modelo.

## Solución

El usuario dibuja un número del 0 al 9 en un canvas HTML. Al hacer clic en "Adivinhar" (Adivinar), el frontend envía la imagen dibujada a un backend en Node.js/Express, que la reenvía a un servicio separado en Python (FastAPI) responsable de cargar el modelo entrenado (Keras/TensorFlow) y devolver el dígito predicho.

## Decisiones técnicas

Separar la inferencia de IA en un servicio Python propio, independiente del backend en Node, permite usar bibliotecas de IA nativas del ecosistema Python (TensorFlow/Keras) sin forzarlas dentro del runtime de JavaScript. El backend en Node actúa solo como intermediario/gateway, encargándose de la carga de archivos (Multer) y de reenviarlos al servicio de IA.

## Resultado

La aplicación funciona correctamente de punta a punta, probada localmente dibujando dígitos y verificando la predicción del modelo. La demo pública tiene una limitación: el servicio de IA alojado en Railway está caído (el despliegue gratuito expiró), así que la predicción falla en producción aunque el resto de la aplicación esté en línea con normalidad. Bug documentado en la [issue #1 de mnist-classifier-ai](https://github.com/felipe-sant/mnist-classifier-ai/issues/1).

## Aprendizajes

Diseñar la arquitectura de un sistema políglota (Node.js + Python) con responsabilidades bien separadas, y lidiar con los desafíos de mantener en línea varios servicios alojados en distintos planes gratuitos al mismo tiempo.

### ARCHITECTURE.md

## Visión general

El proyecto se divide en tres servicios independientes, cada uno en su propio repositorio:

- mnist-classifier-front — React. Canvas de dibujo y presentación del resultado.
- mnist-classifier-back — Node.js/Express. Recibe la imagen mediante carga (Multer) y la reenvía al servicio de IA.
- mnist-classifier-ai — Python/FastAPI. Carga el modelo entrenado (Keras/TensorFlow) y devuelve la predicción.

## Flujo de datos

1. El usuario dibuja en el canvas (front).
2. El front convierte el canvas en imagen y la envía por POST al back (`/ia/predict`).
3. El back reenvía la imagen, vía multipart/form-data, al servicio de IA (`/predict`).
4. La IA preprocesa la imagen (escala de grises, redimensionamiento a 28x28, normalización) y ejecuta la inferencia en el modelo.
5. El resultado (dígito predicho) vuelve por la misma cadena hasta el front.

## Por qué tres servicios separados

El back en Node no tiene un runtime adecuado para ejecutar modelos TensorFlow/Keras directamente. Separar la IA en un servicio Python permite usar las bibliotecas nativas del ecosistema, manteniendo el back en Node como una capa delgada de integración (carga, validación, enrutamiento) entre el front y la IA.

### README.md

## Contexto

Proyecto de hobby, hecho solo por diversión en un único día: un sitio de "pedido de noviazgo imposible de rechazar", donde el botón de rechazo huye del cursor cada vez que el usuario intenta acercarse.

## Mi rol

Lo desarrollé yo solo, desde cero hasta el despliegue.

## Solución

Al pasar el mouse cerca del botón "Não" (No), su posición se recalcula aleatoriamente dentro de la pantalla, lo que vuelve prácticamente imposible hacer clic en él. El botón "Sim" (Sí) acepta la invitación y redirige a una canción.

## Decisiones técnicas

La lógica de "huida" es simple y directa: en el evento de mouseover (y en el clic, como seguridad extra), el botón recibe una nueva posición absoluta generada aleatoriamente dentro de una franja segura de la pantalla, mediante una función utilitaria de generación de posición.

## Resultado

Proyecto pequeño y funcional, publicado y en línea.

## Aprendizajes

A veces un proyecto no necesita resolver un problema serio para ser un buen ejercicio de frontend. Fue una forma ligera de practicar la manipulación del DOM y el posicionamiento dinámico de elementos.

### README.md

## Contexto

Proyecto académico para practicar operaciones CRUD completas (crear, listar, editar, eliminar) con una base de datos NoSQL, construyendo tanto el frontend como la API.

## Mi rol

Desarrollé yo solo el frontend y el backend.

## Solución

La aplicación permite registrar gastos (descripción, fecha y valor), listar todos los gastos registrados, y editar y eliminar cada uno. El frontend consume una API REST propia, que persiste los datos en MongoDB mediante Mongoose.

## Decisiones técnicas

Separación clara entre frontend y backend en repositorios propios, unidos por un repositorio contenedor con git submodules. El backend expone una API REST simple en Express, y el frontend usa React puro (sin bibliotecas de estado), con llamadas directas a la API.

## Resultado

El CRUD funciona de punta a punta, probado creando, listando y confirmando la persistencia de un gasto. La interfaz, sin embargo, todavía está a nivel de prototipo (sin estilos reales, con textos de relleno como "Hello world"), por lo que el proyecto está marcado para un retrabajo visual futuro.

## Aprendizajes

La idea y la base funcional del proyecto son sólidas. La mayor carencia hoy es solo de acabado de la interfaz, no de lógica ni de arquitectura.

### README.md

## Contexto

Proyecto académico para practicar el manejo de estado y formularios en React: convertir entre sí unidades de longitud, peso y temperatura.

## Mi rol

Lo desarrollé yo solo, frontend puro, sin backend.

## Solución

El usuario elige una categoría (longitud, peso o temperatura), ingresa un valor y la unidad de origen, y el sistema calcula y muestra el valor convertido en la unidad de destino. Un botón permite invertir rápidamente la unidad de origen y la de destino.

## Decisiones técnicas

Toda la lógica de conversión se ejecuta en el cliente, sin necesidad de una API externa. Las fórmulas de conversión entre unidades son fijas y conocidas, así que no hay motivo para depender de un servicio externo para esto (a diferencia de las conversiones que dependen de datos actualizados, como las de moneda).

## Resultado

Funciona como se esperaba, probado convirtiendo longitud (km a m).

## Aprendizajes

Un proyecto pequeño, pero útil para reforzar que no toda funcionalidad "de conversión" necesita una API: a veces la lógica pura ya lo resuelve, con menos puntos de falla.

## Proyecto: Player Profile Clustering

**Ficha técnica**

- Stack - Infra y herramientas: Python, scikit-learn, pandas

**Enlaces**

- Repositorio: https://github.com/felipe-sant/player-profile-clustering-ai

**Galería**

**Documentación**

### README.md

## Contexto

Proyecto personal para aplicar aprendizaje no supervisado (K-Means) a un problema real de ciencias del deporte: agrupar atletas de fútbol en perfiles de rendimiento físico a partir de métricas de sesión (distancia recorrida, sprints, velocidad máxima, intensidad), para apoyar decisiones tácticas y ajustes de entrenamiento.

## Mi rol

Desarrollé yo solo todo el pipeline: desde el entrenamiento del modelo en Python hasta la API de inferencia en producción. La API está en un repositorio propio, [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service), y consume el modelo exportado por este.

## Solución

El modelo se entrenó en Python con scikit-learn (pipeline de normalización + K-Means con 4 clusters), incluyendo una métrica derivada de "explosividad" calculada a partir de la distancia de sprint y la velocidad máxima. Los clusters resultantes se nombran automáticamente según las características de los centroides (por ejemplo, alta intensidad y sprint corto = "explosivo"). El modelo entrenado se exporta al formato ONNX y se sirve mediante una API en Node.js/TypeScript, que ejecuta la inferencia con ONNX Runtime sin depender de Python en producción. También calcula el perfil predominante de un atleta a lo largo de varios partidos, consultando una base de datos PostgreSQL.

## Decisiones técnicas

Exportar el modelo a ONNX y ejecutar la inferencia en Node.js (en lugar de mantener un servicio Python en producción) simplifica el despliegue y evita mantener dos runtimes distintos en ejecución. Los parámetros del normalizador (media y desviación estándar) se exportan junto con el modelo, para garantizar que el preprocesamiento en producción sea idéntico al del entrenamiento.

## Resultado

Probado con múltiples perfiles de entrada sintéticos: las métricas de alta intensidad y sprint corto se clasificaron correctamente como "explosivo", mientras que las métricas de larga distancia y baja intensidad se clasificaron como "resistente", lo que confirma que el modelo distingue los perfiles de forma coherente.

## Aprendizajes

Nombrar los clusters automáticamente según las características de los centroides (en lugar de etiquetarlos manualmente después de cada entrenamiento) vuelve el pipeline más robusto frente a reentrenamientos con datos distintos.

### ARCHITECTURE.md

## Visión general

El proyecto se divide en dos partes, en repositorios separados:

- [player-profile-clustering-ai](https://github.com/felipe-sant/player-profile-clustering-ai) — Python. Notebook de entrenamiento del modelo K-Means, exportación a ONNX.
- [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service) — Node.js/TypeScript. API que ejecuta la inferencia del modelo exportado y consulta métricas de atletas en PostgreSQL.

## Flujo de datos

1. Las métricas de sesión se cargan desde una planilla (`players.xlsx`) y se filtran (por ejemplo, partidos con un volumen mínimo de distancia).
2. Se calcula una métrica derivada ("Explosividade", explosividad) a partir del sprint, la distancia y la velocidad máxima.
3. Las métricas se normalizan (StandardScaler) y se usan para entrenar un K-Means con 4 clusters.
4. Los clusters se nombran automáticamente según las características de los centroides (por ejemplo, alta intensidad y sprint corto = "explosivo").
5. El pipeline entrenado (normalización + K-Means) se exporta a ONNX, junto con los parámetros del normalizador.
6. El servicio Node.js carga el modelo ONNX mediante `onnxruntime-node`, normaliza los datos de entrada con los mismos parámetros del entrenamiento, ejecuta la inferencia e interpreta el resultado (cluster + confianza).

## Por qué ONNX en lugar de mantener un servicio Python

Ejecutar la inferencia en Node.js evita mantener dos runtimes (Python + Node) en producción. El modelo entrenado en Python se exporta una sola vez, y el servicio que lo consume no necesita ninguna dependencia de IA además de ONNX Runtime.

### SETUP.md

## Entrenamiento del modelo (opcional)

```bash
cd player-profile-clustering-ai
pip install -r requirements.txt
```

Abre y ejecuta `src/k-means_model.ipynb` (Jupyter). Genera `model/player-profile-clustering.onnx` y `model/scaler_params.json`.

## Servicio de inferencia

```bash
cd player-profile-clustering-service
npm install
```

Crea un `.env` con:

```env
POSTGRESQL_URL=tu_connection_string_de_postgres
```

La variable es obligatoria solo para el endpoint `/api/athlete/metrics`; `/api/match/predict` funciona sin base de datos, solo con el modelo.

```bash
npm run dev
```

Se inicia en `http://localhost:3000`.

## Probando la predicción sin base de datos

```bash
curl -X POST http://localhost:3000/api/match/predict \
  -H "Content-Type: application/json" \
  -d '{"distanceM": 9500, "highIntensityRunningM": 1200, "highIntensityEvents": 35, "sprintDistanceM": 450, "numberOfSprints": 18, "topSpeedKph": 32.5, "avgSpeedKph": 7.2, "accelerations": 40, "decelerations": 38, "metresPerMinuteM": 105, "workloadIntensity": 0.78}'
```
