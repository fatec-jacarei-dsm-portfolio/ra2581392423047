### README.md

## Context

Academic project to practice geographic calculation and frontend-backend integration: simulating a real flight route between two random points in Brazil, taking the curvature of the Earth into account instead of a straight line on a Cartesian plane.

## My role

I developed both the frontend and the backend on my own.

## Solution

The frontend renders the map with Leaflet, lets the user enter coordinates manually or click directly on the map, and simulates the aircraft's path in real time. The backend provides valid coordinates within Brazilian territory and, on every position update, returns geographic information (country, state, municipality, microregion and mesoregion) from the IBGE API.

## Technical decisions

The position along the route is calculated with spherical interpolation (Slerp) over the great-circle arc between the two coordinates, instead of linear interpolation. This guarantees that the path represents the real curvature of the Earth, not a straight line on a Cartesian plane. The backend was rewritten in December 2025, structured in layers of routes, controllers and services, with unit tests using Jest.

## Outcome

The frontend is live and works on its own, but it points to a previous version of the backend (old routes), since the backend was rewritten after the last frontend adjustment. Because of that, the location panel during the flight always returns "Desconhecido" (Unknown), a bug documented in [issue #3](https://github.com/felipe-sant/maps-front/issues/3).

## Learnings

Understanding the difference between linear and spherical interpolation for geographic calculations, and the importance of keeping frontend and backend in sync when they are separate repositories. The compatibility break was only noticed in a later review of the projects.

### README.md

## Context

Personal project to practice the full cycle of an AI product: training a handwritten digit recognition model and exposing it in an interactive web application, from the drawing to the prediction.

## My role

I developed all three layers on my own: the frontend (drawing canvas), the backend (intermediary between front and AI) and the Python inference service, in addition to training the model.

## Solution

The user draws a number from 0 to 9 on an HTML canvas. When clicking "Adivinhar" (Guess), the frontend sends the drawn image to a Node.js/Express backend, which forwards it to a separate Python service (FastAPI) responsible for loading the trained model (Keras/TensorFlow) and returning the predicted digit.

## Technical decisions

Separating AI inference into its own Python service, independent from the Node backend, makes it possible to use AI libraries native to the Python ecosystem (TensorFlow/Keras) without forcing them into the JavaScript runtime. The Node backend acts only as an intermediary/gateway, handling file upload (Multer) and forwarding it to the AI service.

## Outcome

The application works correctly end to end, tested locally by drawing digits and checking the model's prediction. The public demo has a limitation: the AI service hosted on Railway is down (free deploy expired), so the prediction fails in production even though the rest of the application is up normally. Bug documented in [issue #1 of mnist-classifier-ai](https://github.com/felipe-sant/mnist-classifier-ai/issues/1).

## Learnings

Architecting a polyglot system (Node.js + Python) with well-separated responsibilities, and dealing with the challenges of keeping several services hosted on different free plans up at the same time.

---

### ARCHITECTURE.md

## Overview

The project is split into three independent services, each in its own repository:

- mnist-classifier-front — React. Drawing canvas and result display.
- mnist-classifier-back — Node.js/Express. Receives the image through upload (Multer) and forwards it to the AI service.
- mnist-classifier-ai — Python/FastAPI. Loads the trained model (Keras/TensorFlow) and returns the prediction.

## Data flow

1. The user draws on the canvas (front).
2. The front converts the canvas into an image and sends it via POST to the back (`/ia/predict`).
3. The back forwards the image, as multipart/form-data, to the AI service (`/predict`).
4. The AI preprocesses the image (grayscale, resize to 28x28, normalization) and runs inference on the model.
5. The result (predicted digit) returns through the same chain to the front.

## Why three separate services

The Node back does not have a suitable runtime to run TensorFlow/Keras models directly. Separating the AI into a Python service makes it possible to use the ecosystem's native libraries, keeping the Node back as a thin integration layer (upload, validation, routing) between the front and the AI.

### README.md

## Context

Personal project to apply unsupervised learning (K-Means) to a real sports science problem: grouping soccer athletes into physical performance profiles from session metrics (distance covered, sprints, top speed, intensity), to support tactical decisions and training adjustments.

## My role

I developed the whole pipeline on my own: from training the model in Python to the inference API in production. The API lives in its own repository, [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service), and consumes the model exported by this one.

## Solution

The model was trained in Python with scikit-learn (normalization pipeline + K-Means with 4 clusters), including a derived "explosiveness" metric calculated from sprint distance and top speed. The resulting clusters are named automatically based on the characteristics of the centroids (e.g., high intensity and short sprint = "explosivo", explosive). The trained model is exported to the ONNX format and served by a Node.js/TypeScript API, which runs inference through ONNX Runtime without depending on Python in production. It also calculates an athlete's predominant profile across several matches, querying a PostgreSQL database.

## Technical decisions

Exporting the model to ONNX and running inference in Node.js (instead of keeping a Python service in production) simplifies deployment and avoids keeping two different runtimes running. The normalizer parameters (mean and standard deviation) are exported along with the model, to guarantee that preprocessing in production is identical to the one in training.

## Outcome

Tested with multiple synthetic input profiles: high-intensity metrics with short sprints were correctly classified as "explosivo" (explosive), while long-distance, low-intensity metrics were classified as "resistente" (endurance), confirming that the model distinguishes the profiles coherently.

## Learnings

Naming clusters automatically based on the characteristics of the centroids (instead of labeling manually after each training run) makes the pipeline more robust to retraining with different data.

---

### ARCHITECTURE.md

## Overview

The project is split into two parts, in separate repositories:

- [player-profile-clustering-ai](https://github.com/felipe-sant/player-profile-clustering-ai) — Python. K-Means model training notebook, export to ONNX.
- [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service) — Node.js/TypeScript. API that runs inference on the exported model and queries athlete metrics in PostgreSQL.

## Data flow

1. Session metrics are loaded from a spreadsheet (`players.xlsx`) and filtered (e.g., matches with a minimum distance volume).
2. A derived metric ("Explosividade", explosiveness) is calculated from sprint, distance and top speed.
3. The metrics are normalized (StandardScaler) and used to train a K-Means with 4 clusters.
4. The clusters are named automatically based on the characteristics of the centroids (e.g., high intensity and short sprint = "explosivo", explosive).
5. The trained pipeline (normalization + K-Means) is exported to ONNX, along with the normalizer parameters.
6. The Node.js service loads the ONNX model through `onnxruntime-node`, normalizes the input data with the same parameters used in training, runs inference and interprets the result (cluster + confidence).

## Why ONNX instead of keeping a Python service

Running inference in Node.js avoids keeping two runtimes (Python + Node) in production. The model trained in Python is exported once, and the service that consumes it does not need any AI dependency besides ONNX Runtime.
