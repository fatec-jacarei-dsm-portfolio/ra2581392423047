### README.md

## Context

Academic project to practice geographic calculation and frontend-backend integration: simulating a real flight route between two random points in Brazil, taking the curvature of the Earth into account instead of a straight line on a Cartesian plane.

## My role

I developed both the frontend and the backend on my own.

## Solution

The frontend renders the map with Leaflet, lets the user enter coordinates manually or click directly on the map, and simulates the aircraft's path in real time. The backend provides valid coordinates within Brazilian territory and, on every position update, returns geographic information (country, state, municipality, microregion and mesoregion) from the IBGE API.

## Technical decisions

The position along the route is calculated with spherical interpolation (Slerp) over the great-circle arc between the two coordinates, instead of linear interpolation. This guarantees that the path represents the real curvature of the Earth, not a straight line on a Cartesian plane. The backend was rewritten in December 2025, structured in layers of routes, controllers and services, with unit tests using Jest.

## Outcome

The frontend is live and works on its own, but it points to a previous version of the backend (old routes), since the backend was rewritten after the last frontend adjustment. Because of that, the location panel during the flight always returns "Desconhecido" (Unknown), a bug documented in [issue #3](https://github.com/felipe-sant/maps-front/issues/3).

## Learnings

Understanding the difference between linear and spherical interpolation for geographic calculations, and the importance of keeping frontend and backend in sync when they are separate repositories. The compatibility break was only noticed in a later review of the projects.

### README.md

## Context

Personal project to practice the full cycle of an AI product: training a handwritten digit recognition model and exposing it in an interactive web application, from the drawing to the prediction.

## My role

I developed all three layers on my own: the frontend (drawing canvas), the backend (intermediary between front and AI) and the Python inference service, in addition to training the model.

## Solution

The user draws a number from 0 to 9 on an HTML canvas. When clicking "Adivinhar" (Guess), the frontend sends the drawn image to a Node.js/Express backend, which forwards it to a separate Python service (FastAPI) responsible for loading the trained model (Keras/TensorFlow) and returning the predicted digit.

## Technical decisions

Separating AI inference into its own Python service, independent from the Node backend, makes it possible to use AI libraries native to the Python ecosystem (TensorFlow/Keras) without forcing them into the JavaScript runtime. The Node backend acts only as an intermediary/gateway, handling file upload (Multer) and forwarding it to the AI service.

## Outcome

The application works correctly end to end, tested locally by drawing digits and checking the model's prediction. The public demo has a limitation: the AI service hosted on Railway is down (free deploy expired), so the prediction fails in production even though the rest of the application is up normally. Bug documented in [issue #1 of mnist-classifier-ai](https://github.com/felipe-sant/mnist-classifier-ai/issues/1).

## Learnings

Architecting a polyglot system (Node.js + Python) with well-separated responsibilities, and dealing with the challenges of keeping several services hosted on different free plans up at the same time.

---

### ARCHITECTURE.md

## Overview

The project is split into three independent services, each in its own repository:

- mnist-classifier-front — React. Drawing canvas and result display.
- mnist-classifier-back — Node.js/Express. Receives the image through upload (Multer) and forwards it to the AI service.
- mnist-classifier-ai — Python/FastAPI. Loads the trained model (Keras/TensorFlow) and returns the prediction.

## Data flow

1. The user draws on the canvas (front).
2. The front converts the canvas into an image and sends it via POST to the back (`/ia/predict`).
3. The back forwards the image, as multipart/form-data, to the AI service (`/predict`).
4. The AI preprocesses the image (grayscale, resize to 28x28, normalization) and runs inference on the model.
5. The result (predicted digit) returns through the same chain to the front.

## Why three separate services

The Node back does not have a suitable runtime to run TensorFlow/Keras models directly. Separating the AI into a Python service makes it possible to use the ecosystem's native libraries, keeping the Node back as a thin integration layer (upload, validation, routing) between the front and the AI.

### README.md

## Context

Personal project to apply unsupervised learning (K-Means) to a real sports science problem: grouping soccer athletes into physical performance profiles from session metrics (distance covered, sprints, top speed, intensity), to support tactical decisions and training adjustments.

## My role

I developed the whole pipeline on my own: from training the model in Python to the inference API in production. The API lives in its own repository, [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service), and consumes the model exported by this one.

## Solution

The model was trained in Python with scikit-learn (normalization pipeline + K-Means with 4 clusters), including a derived "explosiveness" metric calculated from sprint distance and top speed. The resulting clusters are named automatically based on the characteristics of the centroids (e.g., high intensity and short sprint = "explosivo", explosive). The trained model is exported to the ONNX format and served by a Node.js/TypeScript API, which runs inference through ONNX Runtime without depending on Python in production. It also calculates an athlete's predominant profile across several matches, querying a PostgreSQL database.

## Technical decisions

Exporting the model to ONNX and running inference in Node.js (instead of keeping a Python service in production) simplifies deployment and avoids keeping two different runtimes running. The normalizer parameters (mean and standard deviation) are exported along with the model, to guarantee that preprocessing in production is identical to the one in training.

## Outcome

Tested with multiple synthetic input profiles: high-intensity metrics with short sprints were correctly classified as "explosivo" (explosive), while long-distance, low-intensity metrics were classified as "resistente" (endurance), confirming that the model distinguishes the profiles coherently.

## Learnings

Naming clusters automatically based on the characteristics of the centroids (instead of labeling manually after each training run) makes the pipeline more robust to retraining with different data.

---

### ARCHITECTURE.md

## Overview

The project is split into two parts, in separate repositories:

- [player-profile-clustering-ai](https://github.com/felipe-sant/player-profile-clustering-ai) — Python. K-Means model training notebook, export to ONNX.
- [player-profile-clustering-service](https://github.com/felipe-sant/player-profile-clustering-service) — Node.js/TypeScript. API that runs inference on the exported model and queries athlete metrics in PostgreSQL.

## Data flow

1. Session metrics are loaded from a spreadsheet (`players.xlsx`) and filtered (e.g., matches with a minimum distance volume).
2. A derived metric ("Explosividade", explosiveness) is calculated from sprint, distance and top speed.
3. The metrics are normalized (StandardScaler) and used to train a K-Means with 4 clusters.
4. The clusters are named automatically based on the characteristics of the centroids (e.g., high intensity and short sprint = "explosivo", explosive).
5. The trained pipeline (normalization + K-Means) is exported to ONNX, along with the normalizer parameters.
6. The Node.js service loads the ONNX model through `onnxruntime-node`, normalizes the input data with the same parameters used in training, runs inference and interprets the result (cluster + confidence).

## Why ONNX instead of keeping a Python service

Running inference in Node.js avoids keeping two runtimes (Python + Node) in production. The model trained in Python is exported once, and the service that consumes it does not need any AI dependency besides ONNX Runtime.

### README.md

## Context

Academic project from the 6th semester of the Multiplatform Software Development program at Fatec Jacareí, in partnership with PROCON Jacareí, the city's consumer protection agency. A large share of PROCON's demand comes from recurring questions: what to do about an undue charge, how long the cooling-off period is, which documents to bring. The challenge was a WhatsApp chatbot that would guide consumers through the flows defined by PROCON itself and, when the guidance was not enough, book an in-person appointment.

The challenge came with clear constraints: preferably use the official WhatsApp API, use no external language model API, even a free one, and handle citizens' data in compliance with the LGPD, Brazil's data protection law. The work was done by a team of 7 people, in 3 Scrum sprints, from August to November 2026.

## My role

I was the team's Scrum Master and its main developer: about 1,550 of the nearly 1,700 commits in the repository are mine. I kept the board and the sprint closings up to date, along with requirements traceability, and reviewed the team's PRs.

In the code, I worked on all three parts of the system. In the backend and the WhatsApp gateway, I delivered accounts with granular permissions, cancellation by the staff with a notice to the citizen, rescheduling and cancellation through the chatbot itself, tracking of Meta's delivery statuses, the LGPD features and the AI in the conversation flow. In the admin panel, I built the Users, Opening hours and Chatbot content screens, among others. I also wrote the end-to-end test of the main flow and the PDF manuals handed over to PROCON. I planned and reviewed most of these deliveries with AI agents, using TDD.

## Solution

The citizen sends a message on WhatsApp and the bot leads the conversation with lists and buttons: they pick a category (undue charges, contracts, cooling-off, warranty), then a question, and receive guidance with the legal basis, the required documents and what to do next. If the question is not resolved, the bot offers the free time slots and books the in-person appointment, and the citizen can come back later to reschedule or cancel.

The system has five parts, all running on Docker Compose:

- **WhatsApp gateway:** receives Meta's webhook, checks the signature, processes messages in a per-phone queue and sends the replies.
- **Backend:** keeps the conversation state, builds the answers from the content in the database, calculates the available slots, sends notices to the citizen and serves the panel's API.
- **Local language model:** Ollama, with `llama3.2:3b`, rewrites the explanation of the official answer in a conversational tone.
- **PostgreSQL:** stores content, schedule, conversations and a record of every step for the reports.
- **Web panel:** PROCON's staff manage appointments, edit the chatbot content, configure opening hours, documents, users and the WhatsApp connection, and follow the reports.

Production runs on a cloud VM with HTTPS, and deployment goes through GitHub Actions.

## Technical decisions

- **Official WhatsApp API.** In the first sprint we used an unofficial WhatsApp Web automation. It failed to deliver messages to some contacts and put the number at risk of being banned, so I migrated to the WhatsApp Cloud API before starting the panel. Meta credentials are configured through the panel, stored encrypted, and only saved after a successful connection test.
- **The AI never decides the flow.** The code picks the answer, based on the content registered by PROCON. The model only rewrites the explanation, and the generated text is used only if it includes every number from the official answer and no new number. Every generated answer carries the label "Gerado com auxílio de IA" (generated with AI assistance), and if the model is down or takes too long, the citizen gets the official text.
- **Personal data stored only when needed.** The conversation's phone number becomes a hash, and the CPF (Brazilian taxpayer ID) is kept only as a hash and a masked version. A review showed that Meta's message identifier carries the phone number encoded, so it is also stored only as a hash. The appointment's phone number is deleted once the appointment time arrives, and a time-based anonymization, off by default, clears names and CPFs while keeping the report figures.
- **Concurrency in the schedule.** Booking and rescheduling use PostgreSQL locks per time slot, always taken in the same order, and business rules are checked inside the transaction, after the lock, so two citizens never end up with the same slot.
- **Logical modules, not microservices.** The backend is a single service, split into conversation, decision, schedule, messaging and panel modules. Only the language model has its own container, because it loads the whole model into memory.

## Outcome

The project was delivered on November 23, 2026, with all 16 requirements of the challenge (8 functional and 8 non-functional) completed and the system in production. In the third sprint, 17 of the 22 deliveries had my name among the assignees.

The test suite grew past 3,700 automated cases in Vitest across backend, gateway and panel, with integration tests running against a real PostgreSQL in CI. The end-to-end test simulates Meta's signed webhook, from the first "hi" to the appointment recorded in the panel, and passed in CI on its very first run. A mutation review of that test showed that the formatted CPF was not being checked, and the gap was fixed before the merge.

One limit became clear: on CPU, the local model takes 23 to 38 seconds per answer. That is why the bot shows the typing indicator while it waits, runs one generation at a time and replies with the official text when the AI is busy. The production VM does not have enough memory for the model, so the live version replies only with the official text, unless Ollama on a team machine is connected over a private network.

## Learnings

I learned that a green test does not prove coverage: only changing the code on purpose and watching the test fail shows that it protects the rule. I also learned that a check made outside a lock has to be repeated inside it, and that personal data shows up where you least expect it, such as in a message identifier. As Scrum Master, I saw that the end of a sprint piles up deliveries when documentation and tests are left for later, and I started pulling them earlier.

## Project: claude-kit

### README.md

## Context

I use Claude Code every day, across several repositories, and I kept repeating the same setup in each one: agents, coding rules, skills and `settings.json` tweaks. Over time every copy drifted from the others, and an improvement made in one project never reached the rest. Inspired by my work experience with agent teams, I built a personal kit that brings that team to any repository with a single command.

## My role

I built the project on my own: the `ai-sync` command, the content of the agents, rules and skills, the tests, the lint and the GitHub Actions automation. The kit itself is developed with the team it installs, and the problems that show up when I use the team in other projects become issues in the repository.

## Solution

`ai-sync` is a Node.js script that takes the path of the target repository. It reads the `package.json` and `composer.json` at the root and in first-level folders, detects the stack (React, NestJS, Laravel or AdonisJS) and copies into the `.claude/` folder the agents, rules and skills that fit that project, plus a base Claude Code configuration. Anyone who prefers to choose by hand uses a profile (`default`, `frontend`, `backend` or `tooling`).

After the sync, you just open Claude Code and run `/team-setup`. The skill turns the main session into the orchestrator: it talks to the user, puts together the team for each task and only delegates. The flow goes through the `product-owner`, who defines rules and scope, the `sdd`, who writes the specification, the devs (frontend, backend, mobile, database, devops, fullstack and documentation), who implement with TDD and hand mechanical tasks to the `executor`, and the `reviewer`, mandatory whenever there is a dev on the team. The `qa` and the `designer` join when the task calls for them.

The team keeps a memory per repository, holding only what stays valid after the task, and can run as subagents or, optionally, as an agent team whose members message each other. In the kit's own repository, an agent in GitHub Actions sizes the open issues and opens a pull request only for the small ones.

```bash
node ~/claude-kit/bin/ai-sync.js /path/to/repository
```

## Technical decisions

- **A sync that never deletes anyone's work.** `ai-sync` records in a lock file the path, version and fingerprint (SHA-256) of every installed file. A file edited by the user is never overwritten or removed; the tool only warns that a new version is available. Overwriting requires `--force`, explicitly.
- **A single registration point.** Every agent, rule, skill and stack lives in `catalog.json`, with the rule for which projects it applies to. The lint and the tests check that catalog, files and profiles are consistent.
- **Orchestrator as a skill, not an agent.** At first the orchestrator was an agent opened with `--agent`. I replaced it with a skill loaded into the main session, which leaves a single source for the role and uses the model the session already has.
- **Base configuration without broad permissions.** The `settings.json` template allows no commands or directories, and the lint rejects any template that tries to. What the user has already set is never changed: whatever differs shows up as a suggestion.
- **The kit applies itself.** A pre-commit hook syncs the repository's own `.claude/` on every commit, and a CI test fails an outdated copy.
- **Issue agent with minimal access.** It only reads text from the repository's collaborators, only runs commands from a closed list, has its action pinned by commit hash and never merges.

## Outcome

In five days of development, the repository reached 196 commits, 30 merged pull requests and 41 issues filed, 38 of them already closed. A good share of those issues came from real use of the team in other projects. The kit ships 13 agents, 11 rules (7 general and 4 per stack), 8 skills and 4 profiles, covered by 241 passing automated tests. It is already synced into the repository of ProconChat, a college project, and into the repository I use to record my weekly work.

## Learnings

- An instruction that contradicts itself within the same prompt leaves the agent unsure which order applies. The fix is an explicit, bounded exception, not picking one of the two.
- `git commit -- path` builds a temporary index. A hook that regenerates files from the working folder mixes the work of agents sharing the same worktree; the safe check compares against the exported stage.
- Markdown content also deserves TDD: the test that fails first shows whether the new text really covers the gap in the agent's behavior.
- A repository that applies itself is a good test of its own rules and keeps the copy in use from falling behind.

### SETUP.md

## Prerequisites

Node.js 22 or newer and Claude Code installed. Clone [claude-kit](https://github.com/felipe-sant/claude-kit) into a folder outside the repository that will receive the team:

```bash
git clone https://github.com/felipe-sant/claude-kit.git ~/claude-kit
```

## Apply to a repository

```bash
node ~/claude-kit/bin/ai-sync.js /path/to/repository
```

Inside the repository itself, the path can be omitted. At the end, `ai-sync` shows the detected stacks and what was created, updated, removed and kept. Commit the `.claude/claude-core.lock.json` file along with the repository.

## Set up the team

Open Claude Code in the repository and run `/team-setup`. The main session becomes the orchestrator: it asks for the team's names, proposes who takes part in each task and confirms before delegating.

## Options

| Option           | What it does                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| `--profile name` | Applies a hand-picked profile (`default`, `frontend`, `backend` or `tooling`) instead of stack detection. |
| `--force`        | Also reinstalls the files that were edited in the repository.                                             |
| `--teams`        | Turns on the experimental agent team mode, in the local configuration only. `--no-teams` turns it off.    |
| `--check`        | Checks that the kit's catalog, files and profiles are consistent, without applying anything.              |

Repositories of tools, scripts and content, with no detectable stack, use `--profile tooling`.
